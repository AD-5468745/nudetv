# 텔레그램 채널(nudetv) 종목별 스레드 개편 PRD

**작성일**: 2026-09-23 · **작성**: product-planner (기획만, 코드 변경 없음) · **상태**: 대표님 결정 대기

---

## 0. 대표님 질문 원문

1. "채널에 스포츠 종목별 스레드를 만들고 스레드에 각 경기 앵커를 올리는건 어떨까?"
2. "스레드로 나눠서 자동발송을 할때, 지금처럼 발송량이 많으면 텔레그램 정책상 위반되서 채널이 터지거나 입장불가한 경우가 생기지는 않는가?"

---

## 1. 문제 정의 (Problem)

지금 채널은 경기마다 **앵커(사진 카드) 한 장**만 채널에 올라가고, 분석·라인업·킥오프·득점·구간·종료 같은 세부 콘텐츠는 전부 그 앵커의 **댓글**(연결된 토론방)로 내려간다 (`g1/tick.py` `THREADED_CONTENT_TYPES`, `g1/discussion.py`). 15개 리그(야구 3·축구 9·농구 1·배구 2)가 섞여 있어 채널을 스크롤하면 종목이 뒤섞인다. 대표님은 손님이 **원하는 종목만 골라 보게** 하고 싶어 하시고, 동시에 **자동발송량이 늘면 텔레그램 정책 위반으로 채널이 망가지지 않을지** 걱정하신다.

두 질문은 성격이 다르다 — ①은 "구조를 어떻게 나눌까"(제품 설계), ②는 "지금 설계가 안전한가"(리스크 검증)다. 이 문서는 둘을 분리해서 답한다.

## 2. 타깃 사용자 (Who)

- **채널 구독자** — 특정 종목(예: 야구만)에만 관심 있는 사람과 전체 스포츠를 다 보는 사람이 섞여 있다. 지금은 후자에게 최적화돼 있다.
- **대표님(운영자)** — 비개발자 1인 운영. 위험 없이, 관리 부담을 늘리지 않고 개선하고 싶어 한다.

## 3. 목표 (Goals)

- 사용자 목표: 관심 종목 콘텐츠를 더 쉽게 찾아본다.
- 비즈니스 목표: 구독자 이탈(뒤섞인 피드 피로) 감소, 종목별 신규 유입 여지 확보.
- 비목표: 이번 단계에서 코드를 바꾸지 않는다(기획만). 발송 로직·레이트리밋 방어 로직 자체를 흔들지 않는다.

## 4. 성공 지표 (Metrics)

- **확인못함** — 지금 이 채널에 종목별 클릭률·이탈률 같은 것을 재는 계측이 없다(코드에서 확인한 범위 내). 옵션을 고르기 전에 "무엇을 어떻게 잴지"부터 정해야 나중에 효과를 판단할 수 있다.
- 제안(측정 인프라가 생긴다면): 종목별 앵커 버튼 클릭수, 오늘의 경기 고정글에서 종목 섹션별 클릭수, 구독자 증감 추이.

## 6. A. 기술적으로 가능한가

### 6-1. 사실 확인 — 채널은 포럼(토픽)을 지원하지 않는다

텔레그램 Bot API 공식 문서 확인 결과:

> `Chat.is_forum` — "True, if the **supergroup** chat is a forum (has topics enabled)"
> `Message.message_thread_id` — "…for **supergroups and private chats only**"

**채널(channel) 자체에는 포럼 토픽 기능이 없다.** 포럼은 슈퍼그룹과 봇과의 개인 대화에서만 된다. 즉 "채널 글이 종목별 스레드에 나뉘어 보인다"는 그림은 **텔레그램 구조상 원천적으로 안 된다** — 채널 글은 언제나 하나의 목록이다. (판정: **통과** — 공식 문서로 확인)

나눌 수 있는 것은 채널에 **연결된 토론 그룹**뿐이다(그 그룹은 슈퍼그룹이라 포럼 전환 대상이 될 수 있다). 그런데 지금 그 토론 그룹은 이미 "경기 앵커 1개 ↔ 그 경기 댓글 스레드 1개"로 쓰이고 있다(위 5번 표). 종목별 포럼 토픽을 새로 만들면 **경기 단위 스레드와 종목 단위 토픽, 두 가지 축이 겹친다.**

### 6-2. 안 3개 비교

**① 연결 토론방을 포럼으로 바꿔 종목별 토픽**

- 좋아지는 것: 사람이 토론방 안에서 종목별로 몰아 대화를 볼 수 있다.
- 잃는 것: 지금의 "이 앵커 → 이 경기만의 댓글" 1:1 구조가 깨진다. 종목 토픽 하나에 그 종목의 **여러 경기 세부 카드가 섞여** 들어가므로, 손님이 "이 댓글이 어느 경기 것인지"를 다시 찾아야 한다 — 지금 구조가 없애려던 문제(정보가 뒤섞임)가 다른 축에서 되살아난다.
- 바꿔야 하는 곳: `g1/discussion.py` 전면 재작성(포럼 토픽 id 관리용 상태 파일 신설, `comment_link`→토픽 딥링크로 교체), `g1/tick.py`의 `_thread_for`(2711행)·`THREADED_CONTENT_TYPES` 라우팅을 "경기 기준"에서 "종목 기준"으로 교체, 앵커 버튼 URL 체계 교체.
- **확인못함**: 이미 만들어진 일반 그룹을 봇 API로 "포럼 모드"로 전환할 수 있는지(문서에서 `createForumTopic`·`editForumTopic`은 확인했지만, 그룹 자체를 포럼으로 켜는 API는 이번 조사에서 못 찾았다). 안 되면 대표님이 텔레그램 앱에서 직접 켜야 한다(5분 안팎 작업으로 추정되나 미확인).
- 리스크: **높음.** 구현 범위가 가장 크고, 지금 이미 잘 도는 앵커-댓글 매칭 로직을 걷어내는 것이라 회귀 위험이 크다.

**② 종목별 채널 분리 (야구 채널 / 축구 채널 / 농구·배구 채널 등)**

- 좋아지는 것: 구독자가 원하는 종목 채널만 구독 — 가장 명확한 필터링. 지금의 앵커+댓글 패턴(검증된 구조)을 각 채널에 그대로 복제하면 된다.
- 잃는 것: 구독자가 여러 채널로 쪼개진다(재가입 유도 필요), 채널·토론방·비밀값·모니터링이 종목 수만큼(3~4배) 늘어 운영 부담이 커진다. "한 곳에서 전체 스포츠를 본다"는 지금의 장점이 사라진다.
- 바꿔야 하는 곳: `DISCUSSION_CHAT_ID`·채널 chat_id 등 지금 "채널 1개-토론방 1개" 전제로 짜인 설정 전부를 "리그→채널" 매핑 구조로 바꿔야 한다. `Sender`(`g1/sender.py`)가 채널 하나만 담당하는 구조도 다중화해야 한다.
- 리스크: **매우 높음** (운영 부담이 배로 늘고, 개발 범위도 가장 크다).

**③ 지금 구조 유지 + 종목 태그·필터 (추천)**

- 방법: (a) 앵커 카드·댓글에 종목 해시태그(`#야구` `#축구` 등)를 붙여 채널 안 검색으로 걸러 보게 한다. (b) 이미 있는 "오늘의 경기" 고정글(`_index_links`, `g1/tick.py:2488`)에 종목별 섹션을 나눠 앵커 링크를 묶는다 — game_id→링크 매핑 구조가 이미 있어서 **그룹핑 렌더 한 곳만 손보면 된다.**
- 좋아지는 것: 위험이 가장 작다. 경기 앵커-댓글 1:1 구조를 그대로 보존한다. 발송량·레이트가 전혀 안 늘어난다(추가 발송 없음).
- 잃는 것: "종목별 대화방"처럼 사람이 모여 얘기하는 공간이 생기는 건 아니다 — 순수 탐색성 개선이다. 대표님이 진짜 원하시는 게 "종목별 커뮤니티 공간"이라면 이 안만으로는 부족할 수 있다.
- 리스크: **낮음.**

### 6-3. 판정 요약

| 질문 | 판정 | 근거 |
|---|---|---|
| 채널 자체에 종목별 스레드(토픽)를 만들 수 있는가 | **실패** (텔레그램 구조상 불가) | Bot API 문서 — 포럼은 슈퍼그룹 전용 |
| 연결 토론방을 포럼으로 바꿔 종목별 토픽을 만들 수 있는가 | **통과** (토론방은 슈퍼그룹이라 대상은 됨) 단 전환 절차는 **확인못함** | Bot API 문서 + 조사 한계 |
| 지금 구조를 유지하며 종목 필터링을 개선할 수 있는가 | **통과** | 기존 daily_index 구조 재사용 가능 |

## 7. B. 터지지 않는가 (더 중요한 질문)

### 7-1. 텔레그램 공식 한도 (Bots FAQ 확인)

> "In a single chat, avoid sending more than one message per second."
> "In a group, bots are not be able to send more than 20 messages per minute."
> "For bulk notifications, bots are not able to broadcast more than about 30 messages per second, unless they enable paid broadcasts."
> 한도를 넘기면 **429 오류**(일시적 지연 — `retry_after`만큼 기다렸다 재시도)가 온다. 유료 브로드캐스트를 켜면 초당 1000건까지 늘릴 수 있으나 **이 채널은 안 쓰고 있다**(코드에서 확인).

### 7-2. 지금 코드가 실제로 얼마나 쓰고 있나 — 숫자로

- **발송 속도(코드가 강제하는 값)**: 초당 1건·분당 20건, 그것도 **채널+토론방 전체를 합쳐** 하나의 페이서가 관리한다(`g1/sender.py:1066,1208,1213`). 이는 텔레그램 공식 "단일 채팅 초당 1건" 권장치와 같거나 **더 보수적**이다 — 왜냐하면 실제로는 채널과 토론방이 서로 다른 채팅(chat)이라 텔레그램 기준으로는 각각 초당 1건씩 총 초당 2건까지 여유가 있는데, 지금 코드는 그 둘을 합쳐 초당 1건으로 더 세게 죄고 있다.
- **하루 실제 발송량**(`state/ledger.jsonl` 실측, SENT 상태 기준):

  | 날짜(KST 기준 UTC 일자) | 발송 건수 |
  |---|---|
  | 09-17 | 142 |
  | 09-18 | 110 |
  | 09-19 | 285 |
  | 09-20 | 309 |
  | 09-21 | 29 ⚠️ |
  | 09-22 | 60 ⚠️ |
  | 09-23 | 23 ⚠️ (오늘, 아직 진행 중) |

  ⚠️ 09-21~23이 낮은 것은 **정상적인 감소가 아니다** — `g1/tick.py`의 v1.85 주석에 적힌 실제 사고("2026-09-23 대장 되감김으로 채널 12시간 정지")와 겹치는 기간이라, 그 사고가 없었을 때의 정상치는 09-17~20 평균(**하루 약 211건**, 최대 309건)으로 보는 게 맞다. 최근 7일 그대로 평균 내면 하루 137건인데, 이 숫자는 **사고로 눌린 값**이라 이번 분석의 기준으로 쓰지 않는다.
- **최대 하루 309건**을 초당으로 풀면 `309 ÷ 86,400초 ≈ 초당 0.0036건` — 텔레그램의 "단일 채팅 초당 1건" 한도의 **0.36%**, "전역 초당 30건" 한도의 **0.012%**밖에 안 쓴다.
- 09-20 실제 타임스탬프를 확인해 보니, 메시지가 몰리는 구간에서도 (예: `12:34:37 → 12:34:40 → 12:34:43 …`) **2~3초 간격**을 유지한다 — 코드의 초당 1건 제한이 실제로 지켜지고 있다는 증거다.
- **하루 총량 상한** 자체는 텔레그램 공식 문서에 없다(이번 조사에서 확인한 범위 내) — 텔레그램이 문제 삼는 건 **순간 속도(초당·분당)**이지 하루 총 건수가 아니다. 즉 "발송량이 많아서" 자체는 텔레그램 정책 위반 사유가 아니고, **속도가 빨라야** 문제가 된다. 지금 설계는 총량이 얼마든 순서대로 초당 1건씩 늘어놓기만 하므로, 총량이 늘면 **하루 안에 다 못 보내고 밀릴 위험**은 있어도(자체 안전장치 `DAILY_MAX_MESSAGES=500`이 그 천장을 잡아 준다) **텔레그램이 채널을 막는 위험**과는 다른 문제다.

**판정: 통과** — 지금 설계는 텔레그램 공식 속도 한도보다 보수적으로 짜여 있고, 실측 사용률은 한도의 1% 미만이다.

### 7-3. 스레드로 쪼개면 이 수치가 어떻게 달라지나

- 채널+토론방을 합친 **총 메시지 수는 그대로**다(콘텐츠 종류·수는 안 바뀌고 보낼 곳만 바뀐다). 페이서도 **전체 발송을 하나로** 관리하므로(7-2), 스레드를 나눈다고 초당 속도가 줄거나 늘지 않는다 — **거의 무변화**.
- 오히려 포럼 토픽 안(①안)을 쓰면 토픽 생성·수정(`createForumTopic` 류) 같은 **관리용 API 호출이 소량 추가**된다. 하루 몇 건 수준이라 영향은 미미하지만, 방향은 "줄어든다"가 아니라 "아주 조금 는다"다.
- ②안(채널 분리)은 채널마다 별도 페이서·폭주차단기를 두게 되므로 **채널 하나당 속도는 오히려 여유가 생긴다** — 다만 이건 지금 위험이 크지 않은 문제를 풀려고 운영 부담을 늘리는 것이라 배보다 배꼽이 크다.

**결론: 스레드로 나눈다고 "터지지 않는가"의 위험이 줄어드는 게 아니다.** 지금도 이미 안전하고(7-2), 나눠도 그 안전 여백은 거의 그대로다. 즉 ②의 우려("스레드로 나누면 위반될까")를 해결하려고 구조를 바꿀 필요는 없다 — 지금 그대로도 이미 충분히 안전하다.

### 7-4. "채널이 터지거나 입장불가"가 실제로 일어나는 경로

| 경로 | 확인 여부 | 내용 |
|---|---|---|
| 429 레이트리밋 | **통과(확인)** | 일시적 지연일 뿐이다. `retry_after`초 기다렸다 다시 보내면 되고, 채널이 막히거나 구독자가 못 들어오는 것과 무관하다. 코드도 이미 429를 재시도 카운터에서 제외하는 등 전용 처리를 하고 있다(`g1/sender.py` 주석 4번 규칙). |
| 봇/채널이 스팸으로 자동 제한 | **확인못함** | "메시지 몇 건을 넘기면 자동으로 채널이 막힌다"는 식의 공식 임계값은 이번 조사에서 찾지 못했다. |
| 사람 신고 → 텔레그램 사람 검토 후 제한 | **통과(확인, 단 간접 근거)** | 텔레그램의 계정·채널 제한은 대체로 신고가 쌓인 뒤 **사람이 검토해서** 결정하는 구조로 알려져 있다(공식 FAQ 원문이 아닌 2차 자료 기준이라 확실성은 낮다 — 참고용). 자동으로 "발송 속도가 빠르다"는 이유만으로 즉시 폐쇄되는 사례는 확인되지 않았다. |
| 자기 소유 채널에 관리자 권한으로 글 올리는 행위 자체가 남용으로 분류 | **확인못함** | 텔레그램이 스팸으로 보는 행위(신규 대화 대량 시작, 초대 스팸 등)는 대개 "낯선 사람에게 먼저 접근"하는 패턴이다. 자기가 관리하는 채널에 정기적으로 콘텐츠를 올리는 지금 방식이 이 범주에 든다는 근거는 찾지 못했지만, 공식적으로 "절대 아니다"라고 명시한 문서도 못 찾았다 — 그래서 확인못함으로 남긴다. |

## 8. 우선순위 (MoSCoW)

- **Must**: 없음 — 이번 문서는 기획이며, "지금 구조가 위험하다"는 근거가 없으므로 당장 뭔가를 고쳐야 할 필요는 없다.
- **Should**: 옵션 ③(종목 태그 + 오늘의 경기 종목별 섹션) — 위험 없이 탐색성을 개선한다.
- **Could**: 옵션 ①(토론방 포럼 전환) — "종목별 사람 대화 공간"이 진짜 목적이라면 별도 프로젝트로.
- **Won't (이번 라운드)**: 옵션 ②(채널 분리) — 운영 부담 대비 이득이 낮다.

## 9. 리스크 & 가설

- 가설: 종목 태그만으로도 "내가 원하는 것만 본다"는 요구가 충분히 풀릴 것이다. **미검증** — 대표님/구독자 피드백으로 확인 필요.
- 리스크: 옵션 ①을 고르면 회귀 위험이 큰 재작업이 된다(6-2 참고). 지금 시스템은 앵커-댓글 매칭에서 이미 여러 사고를 겪고 고쳐온 이력이 있다(`g1/tick.py` v1.40·v1.56·v1.60 주석들) — 같은 종류의 구멍이 종목-토픽 매칭에서도 새로 생길 수 있다.
- 리스크: "채널 폐쇄 임계값"이 확인못함으로 남아 있다 — 만약 대표님이 이 부분의 확실한 답을 원하시면, 텔레그램 고객센터/공식 채널에 직접 문의하거나 소규모 테스트 채널로 실측하는 것이 유일한 길이다(공개 문서에 없다).

## 10. 마일스톤 (제안)

- **Phase 1** (위험 없음, 즉시 가능): 옵션 ③ — 종목 해시태그 + 오늘의 경기 종목별 섹션. 구현 규모: `g1/tick.py`의 daily_index 렌더 부분 + 앵커 캡션 생성부 소폭 수정.
- **Phase 2** (대표님 재확인 후): "종목별 대화 공간"이 정말 필요한지 재질문 → 필요하면 옵션 ① 설계에 들어간다. 이때 먼저 "그룹을 포럼으로 전환하는 절차"부터 작게(테스트 그룹 하나로) 확인해 본다.
